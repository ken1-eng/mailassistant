# mailassistant

Gmail の未読メールを Jev で採点して重要度ラベルを付け（① トリアージ）、
予定の連絡をカレンダーに登録する（② カレンダー登録）Google Apps Script。

設計は要件定義ドキュメント「メール→カレンダー自動登録システム 要件定義」に沿っている。
判定は Jev、抽出は生成AI（Claude）、検索と書き込みはコード、という分担。

```
① トリアージ（Jev）─┐ 1リクエストにまとめる
② 予定を含むか（Jev）┘
        │ 大半はここで落ちる
③ 抽出（Claude）       相対日付→実日時、JSON固定、不明はnull
④ 照合（コード）       本カレンダー＋仮登録カレンダーの前後3時間
⑤ 同一判定（Jev）      既存予定1件ずつ。0件なら呼ばない
⑥ 登録（コード）       新規／何もしない／更新／【中止】印／通知のみ
```

## ファイル

| ファイル | 内容 |
|---|---|
| `src/Main.js` | `setup()` / `triageInbox()` / `dryRun()` / `teardown()`、対象メールの検索と処理の流れ |
| `src/Triage.js` | ① の質問、採点（`scoreTriage_`）、期限日数の計算（`daysUntilDeadline_`） |
| `src/Schedule.js` | ② の質問と通過判定、⑤ の質問、⑥ の動作決定（`decideCalendarAction_`） |
| `src/Extract.js` | ③ Claude API 呼び出し、JSON のパースと正規化 |
| `src/Calendar.js` | ④ 既存予定の検索、⑥ 書き込み、通知 |
| `src/Jev.js` | Jev API 呼び出し、criteria の書式チェック、回答の正規化 |
| `src/Log.js` | ログシート（トリアージ用とカレンダー用は別シート） |
| `src/Config.js` | 閾値・上限・ラベル名（すべて暫定値） |

## 導入

1. [clasp](https://github.com/google/clasp) でプロジェクトを作るか既存プロジェクトに紐付ける
   ```sh
   cp .clasp.json.example .clasp.json   # scriptId を書き換える
   npm test && clasp push
   ```
2. スクリプトプロパティを設定する（プロジェクトの設定 → スクリプト プロパティ）

   | キー | 必須 | 内容 |
   |---|---|---|
   | `JEV_API_URL` | ○ | Jev のエンドポイント |
   | `JEV_API_KEY` | ○ | Jev の API キー |
   | `ANTHROPIC_API_KEY` | 段階2以上 | ③ 抽出用 |
   | `CLAUDE_MODEL` | | 既定 `claude-opus-5-5` |
   | `CAL_STAGE` | | カレンダー登録の段階（下表）。既定 `0` = トリアージのみ |
   | `INTERNAL_DOMAINS` | | 社内ドメインをカンマ区切りで。未設定だと全メールが「社外」扱い |
   | `NOTIFY_EMAIL` | | 「通知のみ」をメールで受け取るアドレス。未設定ならログのみ |
   | `START_DATE` | | 開始日カットオフ。`setup()` が実行日を入れる |
   | `LOG_SPREADSHEET_ID` | | ログのスプレッドシート。`setup()` が作って入れる |

3. まず `dryRun()` を手で実行し、ログシートを確認する（ラベル・マーカー・カレンダーには一切書かない）
4. 問題なければ `setup()` を実行する（ラベル・ログシート・5分おきのトリガーを作る）
5. Gmail の画面で `01_即対応` / `02_今日中` に色を付ける（Apps Script からは設定できない）

## カレンダー登録の段階（`CAL_STAGE`）

各段階で必ずドライラン（記録のみ）を挟む。段階3までは何を実行したかではなく
「何をするはずだったか」（`would:create` など）をログに書く。

| 値 | 内容 | 書き込み | 受け入れ条件 |
|---|---|---|---|
| 0 | トリアージのみ | ― | |
| 1 | ② 予定判定を記録 | なし | 30通ほど流し、予定を含むメールの検出漏れがない |
| 2 | ②＋③ 抽出を記録 | なし | 相対日付（来週火曜・明後日・今月末）が正しく変換される |
| 3 | ②〜⑤ 照合まで記録 | なし | 手入力の予定と後から届いた案内が「同一」と判定される |
| 4 | 仮登録カレンダー「Jev仮登録」へ書き込み | 仮登録のみ | 1週間運用して重複がない |
| 5 | 本カレンダーへ書き込み | 本カレンダー | 誤登録率が許容水準になってから |

段階4に上げたら `setup()` をもう一度実行すると仮登録カレンダーが作られる（初回書き込み時にも自動で作る）。
段階4では本カレンダーの既存予定は更新も【中止】印付けもせず、通知のみにする。
中止連絡を受けても予定は削除しない。

## 検証の進め方

ログシートの「自己判定」列を手で埋め、自分の感覚とのズレを見る。閾値（`src/Config.js`）は
分布を見てから決める。追うべき指標は、トリアージは「ラベルが付かなかった中に対応すべきメールがあったか」、
カレンダーは「予定の見落とし」と「重複登録」。

## テスト

```sh
npm test
```

GAS のサービスに触れない純粋関数（採点、期限日数、予定判定の通過、⑥ の動作決定、抽出結果の正規化、
Jev の criteria 書式）を Node で検証する。

## 確認が必要な前提

- **Jev API のリクエスト形式**：既存トリアージスクリプトがこのリポジトリに無いため、
  `POST JEV_API_URL`（`Authorization: Bearer`）、本文 `{ state, questions: [{ name, type, question, criteria }] }`、
  応答 `{ answers: { 質問名: { noul | score | choice, confidence, probabilities } } }` と仮定している。
  既存スクリプトと違う場合は `src/Jev.js` の `buildJevPayload_()` / `jevAsk_()` だけを直せばよい。
- **③ のモデル**：要件定義では未決。Claude（既定 `claude-opus-5-5`、`effort: low`、構造化出力でJSON固定）で実装し、
  `CLAUDE_MODEL` で差し替えられるようにした。拒否時は `fallbacks: "default"` で自動的に別モデルへ回る。
- **要件定義からの追加**：⑤ の `relation` に棄権の選択肢 `cannot_tell` を加えた（質問設計の作法2）。
  ③ の出力に変更前の日時 `previous_start` を加え、変更連絡のときは変更前の時刻の前後も照合する。
- **予定判定は既読メールも対象**：トリアージは既存どおり未読のみだが、予定の見落としを避けるため
  ② 以降は開始日以降の未処理（`_cal` なし）スレッドを既読でも拾う。
